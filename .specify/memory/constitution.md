# NASA NEO Tracker Constitution

## Core Principles

### I. Specification-First Development
Разработка ведётся по спецификации: сначала фиксируются требования, затем
технический план и задачи, и только после этого начинается реализация. Изменения
объёма или поведения сначала отражаются в соответствующих артефактах
спецификации.

### II. Graphical User Interface
Приложение MUST предоставлять графический интерфейс для выбора даты и просмотра
астероидов, сближающихся с Землёй. Реализация пользовательского сценария через
один лишь CLI или скрытые технические средства не считается выполнением
требования.

### III. NASA NeoWs as the Data Source
Данные о сближающихся с Землёй астероидах MUST запрашиваться из NASA NeoWs API.
Интерфейс MUST показывать источник данных, дату данных и время получения ответа,
чтобы пользователь мог оценить актуальность отображаемой информации.

### IV. Input Validation Before Network Access
Ввод пользователя MUST быть проверен до обращения к API. Некорректная или
неполная дата MUST приводить к понятному сообщению в интерфейсе и MUST NOT
вызывать сетевой запрос.

### V. Explicit and Resilient Error Handling
Сетевые ошибки, пустые ответы и ответы некорректного формата MUST обрабатываться
без падения приложения. Пользователь MUST получать понятное сообщение о
проблеме; приложение MUST NOT выдавать ошибку за успешно полученные данные.

### VI. Persistent and Visible Cache
Последние успешно полученные данные MUST сохраняться локально и переживать
перезапуск приложения. Если отображаются данные из кэша, интерфейс MUST явно
обозначать использование кэша и сохранять сведения о дате данных и времени
получения ответа, если они доступны.

### VII. Separation of Concerns and Responsiveness
Графический интерфейс MUST быть отделён от получения данных, разбора ответов,
валидации и хранения кэша. Сетевые запросы MUST выполняться вне потока окна и
не блокировать интерфейс; состояние загрузки и завершение операции должны быть
отражены в интерфейсе.

### VIII. Deterministic Unit Testing
Основная логика, включая валидацию, разбор ответов, обработку ошибок и работу
кэша, MUST покрываться unit-тестами. Тесты MUST запускаться одной командой и
работать без обращения к реальному NASA API; сетевые ответы в тестах
подменяются контролируемыми фикстурами или заглушками.

### IX. Branches and Pull Requests
Каждый этап работы MUST выполняться в отдельной Git-ветке. Слияние изменений
в основную ветку MUST выполняться через Pull Request с проверкой требований,
тестов и соответствия этой конституции.

### X. Traceable Corrections and Agent Errors
Ошибки, допущенные агентом, и ручные исправления MUST фиксироваться в
`REPORT.md` с описанием проблемы, причины, внесённого исправления и способа
проверки. Запись должна позволять сопоставить исправление с этапом работы или
Pull Request.

## Project Constraints

Проект представляет собой графическое приложение NASA NEO Tracker для просмотра
астероидов, сближающихся с Землёй в выбранную пользователем дату. Архитектура и
технологический стек должны поддерживать асинхронное выполнение сетевых
операций, локальное хранение последнего успешного результата и тестирование
основной логики без реального API. Любое отображаемое значение должно иметь
ясный статус: получено из NASA NeoWs, восстановлено из кэша или недоступно.

## Development Workflow

Для каждой функциональности обязательна последовательность:
1. требования и критерии приёмки;
2. технический план и границы компонентов;
3. декомпозиция на задачи;
4. реализация в отдельной ветке;
5. unit-тесты и проверка одной командой без реального API;
6. Pull Request с проверкой конституции и фиксацией необходимых ошибок в
   `REPORT.md`.

Pull Request не должен считаться готовым, если он нарушает обязательный
принцип, оставляет необработанную ошибку пользовательского сценария или
не содержит достаточного описания проверки.

## Governance

Эта конституция является обязательной для требований, планов, задач,
реализации и ревью проекта. При конфликте с локальной практикой проекта
приоритет имеют эти принципы.

Поправка конституции выполняется через отдельный Pull Request. В описании
изменения MUST быть указаны причина, затронутые принципы, влияние на
существующие артефакты и план перехода, если меняется поведение. После
одобрения Pull Request обновляются версия и дата последнего изменения.

Версия использует Semantic Versioning: MAJOR означает несовместимое изменение
или удаление принципа, MINOR — добавление принципа или существенное расширение
правил, PATCH — уточнение формулировок без изменения обязательств. При каждом
ревью проверяются соответствие конституции, тестируемость требований,
обработка ошибок, отсутствие блокировки GUI и актуальность `REPORT.md`.

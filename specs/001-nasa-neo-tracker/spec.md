# Feature Specification: NASA NEO Tracker

**Feature Branch**: `001-nasa-neo-tracker`

**Created**: 2026-10-28

**Status**: Draft

**Input**: User description: "Подготовить спецификацию NASA NEO Tracker для лабораторной работы №3: графическое приложение для просмотра астероидов, сближающихся с Землёй в выбранную пользователем дату, с использованием NASA NeoWs API, валидацией даты, обработкой ошибок, локальным кэшем и unit-тестами без реального API."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Просмотр астероидов за выбранную дату (Priority: P1)

Пользователь открывает приложение, выбирает дату в формате `YYYY-MM-DD` и
нажимает «Получить данные». Приложение получает сведения NASA NeoWs именно за
выбранный день и показывает список астероидов и необходимые характеристики в
таблице.

**Why this priority**: Это основной пользовательский сценарий и ценность
приложения.

**Independent Test**: На заранее подготовленном корректном ответе NASA NeoWs
можно выбрать дату, получить непустой список и проверить все обязательные поля
таблицы и метаданные ответа без реализации остальных сценариев.

**Acceptance Scenarios**:

1. **Given** приложение открыто, **When** пользователь видит поле даты,
   **Then** в нём выбрана текущая локальная дата в формате `YYYY-MM-DD`.
2. **Given** введена существующая дата `2026-10-28`, **When** пользователь
   нажимает «Получить данные», **Then** кнопка становится недоступной, появляется
   индикатор загрузки, а окно остаётся отзывчивым.
3. **Given** NASA NeoWs вернул корректный непустой ответ за выбранную дату,
   **When** загрузка завершена, **Then** таблица содержит название каждого
   астероида, минимальный и максимальный оценочный диаметр в метрах, скорость
   относительно Земли в км/с, расстояние до Земли в километрах и понятный
   признак потенциальной опасности.
4. **Given** данные успешно получены, **When** пользователь просматривает
   результат, **Then** интерфейс показывает выбранную дату, фактическую дату
   данных, источник `NASA NeoWs` и время получения ответа.
5. **Given** в ответе есть несколько записей сближения, **When** приложение
   формирует строку астероида, **Then** используются сведения о сближении именно
   за выбранный день, а данные другого дня не подставляются.

### User Story 2 - Понятная работа с неверной датой (Priority: P1)

Пользователь вводит пустую, неправильно оформленную или несуществующую дату и
получает сообщение об ошибке до любого обращения к NASA NeoWs.

**Why this priority**: Предварительная проверка предотвращает бессмысленные
запросы и делает поведение приложения предсказуемым.

**Independent Test**: Для пустого значения, дат `28-10-2026`, `2026/10/28` и
`2026-02-31` можно проверить, что отображается ошибка, кнопка недоступна и
сетевой клиент не вызывается.

**Acceptance Scenarios**:

1. **Given** поле даты пусто, **When** пользователь изменяет или покидает поле,
   **Then** отображается сообщение о необходимости указать дату, кнопка
   недоступна и сетевой запрос не выполняется.
2. **Given** дата не соответствует формату `YYYY-MM-DD`, **When** пользователь
   вводит её, **Then** отображается сообщение о формате, кнопка недоступна и
   сетевой запрос не выполняется.
3. **Given** введено `2026-02-31`, **When** выполняется проверка, **Then**
   отображается сообщение о несуществующей дате, кнопка недоступна и сетевой
   запрос не выполняется.

### User Story 3 - Безопасное восстановление результата из кэша (Priority: P1)

Если получить свежие данные невозможно или API вернул пустой список, пользователь
видит последний успешно сохранённый результат с явным предупреждением и может
отличить его дату от выбранной даты.

**Why this priority**: Пользователь сохраняет доступ к последнему пригодному
результату, но не вводится в заблуждение относительно его актуальности.

**Independent Test**: После сохранения успешной фикстуры можно имитировать
сетевую ошибку, пустой ответ, повреждённый ответ и перезапуск приложения, а
затем проверить отображение кэша, предупреждений и его метаданных.

**Acceptance Scenarios**:

1. **Given** существует последний успешный кэш за дату `2026-10-27`, **When**
   запрос за `2026-10-28` завершается отсутствием сети, тайм-аутом, HTTP-ошибкой
   или превышением лимита API, **Then** показывается кэш с явным предупреждением,
   выбранная дата остаётся `2026-10-28`, а фактическая дата показанных данных —
   `2026-10-27`.
2. **Given** существует последний успешный кэш, **When** NASA NeoWs возвращает
   пустой список или повреждённый JSON, **Then** предыдущий кэш не уничтожается,
   показывается понятное предупреждение, а результат помечается как кэш.
3. **Given** кэша нет, **When** получение данных завершается ошибкой или пустым
   ответом, **Then** таблица не содержит выдуманных строк и показывается
   сообщение о том, что доступного кэша нет.
4. **Given** кэш сохранён, **When** приложение закрывается и запускается снова,
   **Then** последний успешный результат доступен после запуска с сохранённой
   датой данных и временем получения.
5. **Given** файл кэша повреждён или имеет неверную структуру, **When** приложение
   запускается или пытается прочитать кэш, **Then** приложение не падает,
   повреждённый кэш не показывается как корректные данные и пользователь получает
   понятное сообщение.

### Edge Cases

- Ввод содержит пробелы вокруг даты: приложение либо нормализует их перед
  проверкой, либо сообщает об ошибке; выбранный вариант должен быть единообразным
  и отражён в тестах.
- NASA NeoWs отвечает корректным JSON без ожидаемого раздела с датой или списка
  объектов: ответ считается некорректным, а пригодный кэш сохраняется.
- У отдельного астероида отсутствует название или нельзя определить сближение
  за выбранную дату: запись пропускается с предупреждением.
- У отдельного астероида отсутствует числовое значение: соответствующая ячейка
  показывает «Нет данных», без нуля или другого придуманного значения.
- У отдельного астероида отсутствует признак потенциальной опасности:
  соответствующая ячейка показывает «Неизвестно», а не «Нет».
- Если после пропуска неполных записей пригодных записей не осталось,
  приложение сообщает об этом и использует кэш согласно правилам кэширования.
- В ответе присутствуют записи сближения только за другие даты: данные за
  выбранный день не подменяются другой записью, а результат считается
  неполным/некорректным с понятным сообщением.
- Ответ содержит неизвестные дополнительные поля: они игнорируются и не меняют
  обработку известных полей.
- Повторное нажатие во время загрузки не создаёт второй запрос.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Приложение MUST предоставлять графический интерфейс с полем выбора
  даты, кнопкой «Получить данные», индикатором загрузки, таблицей результатов и
  областью сообщений.
- **FR-002**: Поле даты MUST принимать и отображать дату в формате `YYYY-MM-DD`
  и по умолчанию MUST содержать текущую локальную дату.
- **FR-003**: Приложение MUST проверять заполненность, точный формат и
  существование даты до обращения к NASA NeoWs.
- **FR-004**: При пустой, некорректной или несуществующей дате кнопка получения
  данных MUST быть недоступна, сетевой запрос MUST не выполняться, а сообщение
  MUST объяснять причину.
- **FR-005**: Приложение MUST запрашивать данные только за дату, выбранную
  пользователем.
- **FR-006**: Во время запроса кнопка MUST быть недоступна, отображаться
  индикатор загрузки, а окно MUST оставаться отзывчивым.
- **FR-007**: Источником свежих данных MUST быть NASA NeoWs API.
- **FR-008**: Для каждого отображаемого астероида MUST показываться название,
  минимальный и максимальный оценочный диаметр в метрах, скорость относительно
  Земли в км/с, расстояние до Земли в километрах и значение
  `is_potentially_hazardous_asteroid` в понятном виде.
- **FR-009**: Интерфейс MUST показывать выбранную дату, фактическую дату
  показанных данных, источник `NASA NeoWs` и время получения ответа.
- **FR-010**: Для строки астероида MUST использоваться запись сближения,
  относящаяся к выбранной дате; запись другого дня MUST NOT подставляться.
- **FR-011**: Отсутствующие значения MUST NOT выдумываться. Отсутствующее
  числовое значение MUST отображаться как «Нет данных», отсутствующий признак
  опасности — как «Неизвестно», а запись без названия или без сближения за
  выбранную дату — пропускаться с предупреждением. Нули MUST NOT подставляться.
- **FR-012**: Сетевые ошибки, тайм-ауты, ошибки HTTP, превышение лимита NASA
  NeoWs, повреждённый JSON и неверная структура ответа MUST обрабатываться без
  падения приложения и с понятным сообщением.
- **FR-012a**: Сетевые операции MUST иметь тайм-аут 15 секунд. После тайм-аута
  или другой ошибки интерфейс MUST вернуться в рабочее состояние, а пользователь
  MUST иметь возможность повторить запрос вручную.
- **FR-013**: Успешный корректный непустой ответ MUST сохраняться локально вместе
  с датой данных и временем получения ответа.
- **FR-014**: Приложение MUST сохранять последний пригодный кэш после закрытия и
  восстанавливать его после повторного запуска.
- **FR-015**: При сетевой ошибке или пустом списке приложение MUST показывать
  последний успешно закэшированный день, если он существует, с явной пометкой
  использования кэша и предупреждением. Выбранная дата и фактическая дата кэша
  MUST отображаться раздельно.
- **FR-016**: При отсутствии кэша приложение MUST показывать понятное сообщение
  вместо выдуманного результата.
- **FR-017**: Пустой или некорректный ответ MUST NOT уничтожать предыдущий
  пригодный кэш.
- **FR-018**: Повреждённый кэш MUST обрабатываться без падения приложения и MUST
  NOT отображаться как корректные данные.
- **FR-018a**: На Windows кэш MUST храниться по пути
  `%LOCALAPPDATA%\NASA-NEO-Tracker\cache.json`; каталог MUST создаваться
  автоматически. В unit-тестах путь кэша MUST подменяться временным каталогом.
- **FR-018b**: При использовании `DEMO_KEY` интерфейс MUST показывать сообщение:
  «Используется демонстрационный ключ NASA с ограниченной квотой. Для регулярной
  работы настройте NASA_API_KEY». Реальное значение ключа MUST NOT отображаться
  в интерфейсе, логах или сообщениях.
- **FR-018c**: При превышении квоты NASA API приложение MUST показывать понятное
  сообщение, использовать кэш согласно FR-015 и сохранять возможность повторного
  запроса.
- **FR-019**: Интерфейс MUST быть отделён от получения данных, разбора ответа,
  валидации и хранения кэша; сетевые операции MUST выполняться без блокировки
  окна.
- **FR-020**: Основная логика MUST покрываться unit-тестами, запускаемыми одной
  командой без обращения к реальному NASA NeoWs API.
- **FR-021**: Unit-тесты MUST включать валидацию дат, разбор корректных,
  пустых и некорректных ответов NASA, выбор записи сближения за выбранную дату,
  а также сохранение, чтение и обработку повреждённого кэша.

### Key Entities

- **Выбранная дата**: дата, которую пользователь вводит для запроса; не
  обязательно совпадает с фактической датой данных при показе кэша.
- **Данные сближения**: сведения об одном астероиде за конкретную дату,
  включая название, оценки диаметра, скорость, расстояние и признак опасности.
- **Набор данных**: список данных сближения за одну дату с источником и временем
  получения ответа.
- **Запись кэша**: последний успешно сохранённый непустой набор данных с датой
  данных и временем получения.
- **Статус результата**: состояние результата для пользователя — свежие данные,
  данные из кэша, ошибка или отсутствие данных.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Для корректной даты и корректного ответа все обязательные поля
  каждого отображаемого астероида видны в таблице, а дата сближения соответствует
  выбранной дате в 100% проверяемых сценариев.
- **SC-002**: Для пустой даты, неверного формата и несуществующей даты в 100%
  проверяемых случаев сетевой клиент не вызывается, кнопка недоступна и
  отображается объясняющее сообщение.
- **SC-003**: Во время имитации сетевого запроса окно принимает действия
  интерфейса и не блокируется до завершения операции.
- **SC-004**: В 100% проверяемых сценариев сетевой ошибки, тайм-аута, HTTP-ошибки,
  лимита API, пустого/повреждённого ответа приложение не падает и показывает
  понятный статус.
- **SC-005**: После успешной загрузки и перезапуска последний непустой результат
  восстанавливается с исходной датой данных и временем получения в 100%
  проверяемых сценариев.
- **SC-006**: Пустой, некорректный или повреждённый ответ не удаляет пригодный
  кэш в 100% проверяемых сценариев.
- **SC-007**: Пользователь может отличить свежие данные от кэша по явной
  отметке, а выбранную дату — от фактической даты показанных данных в 100%
  проверяемых сценариев.
- **SC-008**: Единая команда unit-тестов завершается успешно без сетевых
  обращений к NASA NeoWs и проверяет перечисленные в FR-021 области.

## Assumptions

- Приложением пользуется один локальный пользователь; авторизация и управление
  несколькими профилями не входят в область этой лабораторной работы.
- Кэш хранит только последний успешно полученный непустой набор данных.
- Кэш на Windows хранится в `%LOCALAPPDATA%\NASA-NEO-Tracker\cache.json`;
  каталог создаётся автоматически, а тесты используют временный каталог.
- Тайм-аут сетевой операции составляет 15 секунд; после ошибки запрос можно
  повторить вручную.
- Ключ API NASA и правила его хранения определяются планом и не меняют
  пользовательские требования этой спецификации.
- Мобильная и веб-версии, экспорт данных, сортировка, фильтрация и графики не
  входят в минимальный объём функции.
- Реальный NASA NeoWs API не используется в unit-тестах; ответы и ошибки
  заменяются контролируемыми тестовыми данными.
